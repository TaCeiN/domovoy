# Интеграция с ГИС ЖКХ

Справочник по открытой части `dom.gosuslugi.ru`. Все факты ниже **проверены
живыми запросами** 22 августа 2026 года, а не взяты из документации: её
на эти методы не существует.

Отвечает на один вопрос, без которого продукт не работает: **кто управляет
домом**.

---

## Зачем это вообще понадобилось

Первая версия продукта выводила управляющую компанию из ИНН получателя
платежа в QR квитанции. Это **неверно по сути**, и вот почему.

Получатель платежа и управляющая организация — разные лица:

- свет, газ, вода и вывоз мусора идут ресурсникам напрямую по прямым
  договорам (ст. 157.2 ЖК РФ), УК этих денег не видит;
- жилищную квитанцию часто печатает расчётный центр, а не сама УК;
- взносы на капремонт уходят в региональный фонд.

**Доказательство.** ИНН `6167004596` — ГУП РО «ИВЦ ЖКХ», расчётный центр,
который печатает квитанции за ЖКУ по Ростовской области. В справочнике
управляющих организаций ГИС ЖКХ его **нет вовсе**. Организация, чьё имя
стоит в квитанции за ЖКУ, управляющей не является.

Вывод: связку «дом → УК» берём из реестра лицензий, а квитанция отвечает
только на вопросы «какой адрес» и «какой лицевой счёт».

---

## Что доступно без авторизации

Три метода внутренней части портала. Это **не документированный контракт**,
а те же вызовы, которыми ходит сам сайт.

### Обязательные заголовки

```
Accept: application/json
Content-Type: application/json;charset=UTF-8
Session-GUID: <любой uuid>
Request-GUID: <любой uuid>
State-GUID: /houses
```

**Без них портал отвечает 404, а не 401.** Это сбивает с толку: выглядит
как «нет такого метода», хотя метод есть. На этом я потерял час.

### 1. Реестр лицензий — все УК региона

```
POST /rls/api/rest/services/license/public/search
{ "pageIndex": 1, "elementsPerPage": 100,
  "licenseStatuses": [], "houseStatuses": [],
  "address": { "regionCode": "<guid субъекта>" } }
```

Отдаёт организацию целиком: название, ИНН, ОГРН, КПП, телефон, номер
лицензии и `houseCount`. По Ростовской области — **733 лицензии**.

Поля критерия поиска (узнаются отправкой мусорного поля — сервер вернёт
список известных): `houseStatuses`, `licenseStatuses`, `pageIndex`,
`licenseNumber`, `licenseeOrgRootGuid`, `address`, `elementsPerPage`,
`licenseStartDateFrom`, и далее по датам.

Внутри `address` работают: `regionCode`, `cityCode`, `streetCode`,
`houseNumber`, `houseGuid`, `settlementCode`, `areaCode`,
`innerCityAreaCode`, `buildingNumber`, `structNumber`, `formattedAddress`.

**Ловушка:** фильтр по `streetCode` из справочника ФИАС не срабатывает —
у реестра своя иерархия с внутригородскими районами. Фильтровать
надёжно можно по региону и городу.

### 2. Справочник организаций — ИНН в идентификатор

```
POST /ppa/api/rest/services/ppa/organizations/chooser/search;page=1;itemsPerPage=10
{ "sortCriteriaList": [{ "sortedBy": "organizationType", "ascending": false }],
  "organizationTypes": { "coll": ["B","L","A"], "operand": "OR" },
  "subordinationOrgTypeList": { "coll": ["HEAD","BRANCH"], "operand": "OR" },
  "commonSearchString": "<ИНН или название>",
  "pageIndex": 1, "elementsPerPage": 10 }
```

Возвращает `guid`, `fullName`, `shortName`, `inn`, `ogrn`, `kpp`, `status`.
Ответ приходит **то объектом с `items`, то голым массивом** — обрабатывать
надо оба случая, иначе импорт молча привозит ноль при живом ответе.

**Два фильтра, которые нельзя добавлять** (сайт их ставит, а нам они вредят):

| Фильтр | Что теряется |
|---|---|
| `organizationStatuses: ["REGISTERED"]` | 236 организаций со статусом `BLOCKED` |
| `roleConstraints` с `roleCode: "1"` | организации, чья роль не подтверждена |

У заблокированных **дома есть, и в них живут люди**: ООО УО «Ростовгарант»
(BLOCKED) — 9 домов, ООО УК «Результат» (BLOCKED) — 31 дом. Всего по
области 595 домов числятся за заблокированными организациями. Отбросить
их значит оставить этих жителей без управляющей компании в приложении.

### 3. Дома организации

```
POST /homemanagement/api/rest/services/houses/public/searchByOrg?pageIndex=1&elementsPerPage=100
{ "organizationGuid": "<guid из справочника организаций>",
  "calcCount": true, "useReadOnlyDataSource": true }
```

Отдаёт `address.formattedAddress`, `houseGuid`, `residentialPremiseCount`,
тип дома, площадь, состояние.

**Важно:** сюда подходит guid **только из справочника организаций**.
Идентификаторы лицензиата из реестра лицензий (`licensee.orgGuid`
и `licensee.orgRootGuid`) дают ноль домов — проверено на компании,
у которой их 67.

### Что НЕ пригодилось

| Источник | Почему |
|---|---|
| Открытые данные ГИС ЖКХ | 123 набора, все — справочники НСИ. Реестра домов нет |
| Реформа ЖКХ (ППК ФРТ) | Реестр УО есть (CSV, 22 МБ, без регистрации), реестра домов нет |
| Полный ГАР от ФНС | 57 ГБ архив |
| `searchByAddress` | Работает, но фильтр по улице требует иерархии адресов ГИС |
| OpenStreetMap | С этой сети Overpass не отвечает вовсе, Nominatim даёт 503 |

## Коды субъектов

В ГИС ЖКХ **свои** guid субъектов — они не совпадают ни с КЛАДР,
ни с первыми цифрами ИНН. Список в `lib/address/gis.ts`:

| Регион | GUID |
|---|---|
| 61 — Ростовская область | `f10763dc-63e3-48db-83e1-9c566fe3092b` |

Новый регион добавляется туда же. Взять guid можно из ответа
`GET /nsi/api/rest/services/nsi/fias/regions` либо из сетевой панели
браузера на странице реестра.

## Как этим пользуются в проекте

```bash
npm run registry:import -- --region 61            # полный проход, ~час
npm run registry:import -- --region 61 --missing  # догрузить пропущенных
npm run registry:import -- --region 61 --orgs-only
npm run registry:import -- --region 61 --limit 5  # для отладки
```

Импорт **разовый и идемпотентный**: приложение работает на своей копии.
Портал регулярно уходит на регламентные работы и тогда отвечает 200
с пустым телом — жителям это должно быть безразлично.

Клиент — `lib/address/gis.ts`, импортёр — `db/registry-import.ts`,
таблицы — `managing_org` и `managed_house`.

## Сведение адресов: главная ловушка

Реестр пишет **«пр-кт Ленина, д. 85/3»**, квитанция — **«пр-кт Ленина,
д. 85, к. 3»**. Это один дом, но ключи разные.

Масштаб по области: **2156 домов записаны дробью, 971 с корпусом**. Без
обработки каждый шестой житель не нашёл бы свою управляющую компанию.

Решение в `lib/address/normalize.ts` и `lib/auth/bind.ts`:

1. `houseKeyCandidates()` даёт варианты ключа — как есть, дробь→корпус,
   корпус→дробь;
2. поиск по реестру идёт по всем кандидатам;
3. если дом найден — **объекту жителя присваивается ключ ИЗ РЕЕСТРА**.

Третий пункт важнее первых двух. Без него сосед с «85/3» и сосед
с «85, к. 3» оказались бы в разных домах и не увидели бы друг друга.
Реестр — единственный общий источник правды об адресе.

**Дробь при этом не считается корпусом в самом ключе.** На пересечении
улиц дробью нумеруют самостоятельные дома, и слепое слияние поселило бы
чужих людей вместе. Совпадение должно подтвердиться записью в реестре.

Второе расхождение — порядок слов в регионе: реестр пишет «обл Ростовская»,
квитанция «Ростовская обл». Канон один: сначала название, потом тип.

## Что остаётся нерешённым

**Реестр отстаёт от жизни.** Дом сменил УК сегодня — ГИС ЖКХ узнает через
недели. Поэтому в кабинете есть ручное добавление дома
(`POST /api/dispatcher/houses`): чужой дом забрать нельзя, а жители,
привязавшиеся раньше, догоняются автоматически.

**595 домов числятся за заблокированными организациями.** Кто управляет
ими сейчас, реестр не говорит.

**Загружен один регион.** Для второго нужно добавить guid субъекта
и прогнать импорт; универсальность на другом регионе не проверялась.

**Это внутренний API.** Он может измениться без предупреждения. Именно
поэтому импорт разовый, а не запрос в момент входа жителя: портал ляжет —
приложение продолжит работать.
