## API бота

- Авторизация: **только заголовок** `Authorization: <token>`. Документация прямо говорит: «передача токена через query-параметры больше не поддерживается». Query-параметр пока отвечает, но полагаться на него нельзя
- Лимит: 30 запросов в секунду
- Проверено живым `GET /me` — отвечает корректно

### Ловушка с доменом и сертификатом Минцифры

Документация просит слать запросы на **`platform-api2.max.ru`** вместо `platform-api.max.ru`. Но этот домен подписан корневым удостоверяющим центром Минцифры, которого нет в стандартных хранилищах доверенных корней.

Проверено:

| Домен | Результат |
|---|---|
| `platform-api.max.ru` | Работает со стандартными корнями |
| `platform-api2.max.ru` | `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` — и в Node, и в curl |

Это убивает деплой молча: локально всё собирается, а на сервере отваливаются все вызовы к API.

Что нужно сделать до продакшена:
1. Положить корневой сертификат Минцифры в репозиторий
2. Прописать путь в `NODE_EXTRA_CA_CERTS` либо передать PEM в `createCaDispatcher()` из `lib/max/bot-api.ts`
3. Переключить `MAX_API_BASE` на `https://platform-api2.max.ru`

Пока сертификат не добавлен, код работает на старом домене. **Отдельно проверить, что переменная `NODE_EXTRA_CA_CERTS` вообще применима на выбранном хостинге** — на некоторых serverless-платформах её нет, и тогда нужен путь через собственный диспетчер undici, который в клиенте уже предусмотрен.

С 25 мая 2026 платформа также прекращает поддержку вебхуков по HTTP и самоподписанных сертификатов — наш вебхук обязан быть на HTTPS с сертификатом доверенного УЦ.

Нужные нам методы:

| Метод | Зачем |
|---|---|
| `GET /me` | Health-check конфигурации |
| `POST /messages` | Уведомления жителям: статус заявки, отключение воды, напоминание о показаниях |
| `POST /subscriptions` | Webhook для входящих (прод). Отсюда же приходит `chat_id` в событии `bot_started` |
| `GET /updates` | Long polling (только разработка) |

Кнопки передаются вложением `inline_keyboard` в `payload.buttons`. Тип кнопки **`open_app`** открывает мини-приложение — именно им бот зовёт человека внутрь из уведомления. До 210 кнопок в 30 рядах, но не больше **3 в ряду** для типов `link`, `open_app`, `request_contact`, `request_geo_location`.

### Формат кнопки `open_app`

Поля на проводе — **snake_case**, и `web_app` обязателен. Проверено живыми запросами:

| Что отправили | Ответ API |
|---|---|
| без `web_app` | `400 Field 'webApp' cannot be null` |
| только `contact_id` | `400 Field 'webApp' cannot be null` |
| `web_app: "t111_hakaton_bot"` | `404 chat.not.found` — payload принят |

```json
{ "type": "open_app", "text": "Открыть", "web_app": "t111_hakaton_bot", "payload": "req_1" }
```

Ошибка в тексте называет поле `webApp`, а принимает API `web_app` — на этом легко потерять час.

**Откуда брать `chat_id` для отправки уведомления.** Для мини-приложения он приходит в `initData` (объект `chat`) либо в событии подписки `bot_started`. Сохраняем его в момент первого входа — иначе потом уведомление отправить некуда.

## Запуск мини-приложения

Мини-приложение регистрируется в кабинете партнёра: **Чат-боты → Расширенные настройки → URL мини-приложения**. Требования: только `https`, до 1024 символов, латиница, цифры, точка и дефис.

> **Зависимость, которую надо закрыть руками:** пока URL нашего деплоя не вписан в настройки бота, мини-приложение внутри MAX не откроется. Нужен доступ к кабинету партнёра.

Диплинк: `https://max.ru/t111_hakaton_bot?startapp=<payload>` — payload до 512 символов, только `A-Za-z0-9_-`, приезжает в `start_param`.

Используем для:
- `invite_<code>` — приглашение домочадца ссылкой вместо кода голосом
- `req_<id>` — открыть конкретную заявку из уведомления

## Bridge

```html
<script src="https://st.max.ru/js/max-web-app.js"></script>
```

Даёт `window.WebApp` без инициализации.

### Что берём

| Метод | Как используем |
|---|---|
| `initData` | Подписанная строка → валидация на сервере → вход |
| `initDataUnsafe` | Только для отрисовки до ответа сервера. **Доверять нельзя** |
| `openCodeReader(fileSelect)` | **Нативный сканер QR квитанции.** Внутри MAX заменяет `getUserMedia` + jsQR целиком |
| `requestContact()` | **Второй фактор:** телефон, подтверждённый аккаунтом MAX |
| `BackButton.show/hide/onClick` | Нативная кнопка «Назад» вместо нашего трюка с `history.pushState` |
| `shareContent` / `shareMaxContent` | Отправить код приглашения или гостевого доступа контакту в MAX |
| `HapticFeedback.*` | Отклик на отправку заявки и передачу показаний. Нет на десктопе и в вебе |
| `getViewportSize()` | Реальная высота вьюпорта внутри вебвью |
| `getLaunchContext()` | `tabbar` или `default` — источник запуска |
| `enableClosingConfirmation()` | Не терять заполненную форму жалобы при случайном закрытии |
| `platform`, `version`, `deviceName` | Диагностика и телеметрия |

### Чего в Bridge нет

**Темы оформления.** В API нет ни одного метода про тему или цветовую схему — это проверено по полному списку методов. Значит наш переключатель «Системная / Светлая / Тёмная» на `prefers-color-scheme` остаётся единственным механизмом, и внутри MAX тема пойдёт за системной темой устройства.

`DeviceStorage` и `SecureStorage` **не работают в веб-клиенте** — нужен фолбэк на `localStorage`.

## Валидация initData — критическая часть

Подпись проверяется **только на сервере**. Клиентской проверке доверять нельзя ни в каком виде: к `max_user_id` привязан лицевой счёт и платёжные данные.

### Как MAX отдаёт данные

Параметры приезжают во **фрагменте URL**, после `#`:

```
https://our-app.example#WebAppData=<urlencoded>&WebAppPlatform=web&WebAppVersion=26.2.8
```

> **Фрагмент URL браузер на сервер не отправляет.** Клиент обязан прочитать `window.WebApp.initData` и передать строку на бэкенд явно — заголовком или в теле запроса. Это самая частая ошибка при первой интеграции.

Внутри `WebAppData` — строка `key=value&key=value` с полями: `user`, `chat`, `query_id`, `auth_date`, `ip`, `hash`. Поля `user` и `chat` — JSON-объекты.

```jsonc
user: { id, first_name, last_name, username, language_code, photo_url }
chat: { id, type: 'DIALOG' | 'CHAT' | 'CHANNEL' }
```

### Алгоритм

1. Разбить `WebAppData` по `&` на пары `key=value`
2. Убедиться, что `hash` встречается **ровно один раз**; сохранить и исключить его
3. URL-декодировать значения
4. Отсортировать по ключам `a → z`
5. Склеить `key=value` через `\n` (0x0A) → `launch_params`
6. `secret_key = HMAC_SHA256(key: "WebAppData", message: BOT_TOKEN)`
7. `signature = hex(HMAC_SHA256(key: secret_key, message: launch_params))`
8. Сравнить с `hash` — **сравнением с постоянным временем**, не `===`

Дополнительно проверяем `auth_date`: документация рекомендует считать данные протухшими через **1 час**.

Порядок аргументов в шаге 6 обратный привычному: ключ — строковая константа `"WebAppData"`, сообщение — токен бота. Перепутать местами легко, и подпись тогда не сойдётся ни разу.

## Валидация телефона из `requestContact()`

Возвращает `{ phone, authDate, hash }`. Проверка — другая схема, не та же, что у initData:

- сообщение: пары в алфавитном порядке через `\n` → `authDate=<...>\nphone=<...>\nuserId=<...>`
- ключ: **сам токен бота** (без вывода `secret_key`)
- `phone` без `+`: `79991234567`, не `+79991234567`

Ошибки приходят как `{"error":{"code":"client.request_phone.<reason>"}}`, в том числе `user_refused_provide_phone_number`.

## Что это меняет в продукте

### Дыра, которая закрывается

Вход только по QR означал: **у кого квитанция — тот и хозяин**. Поднял чужую платёжку из ящика — увидел чужой адрес, лицевой счёт и историю платежей.

Теперь связка из трёх факторов:

| Фактор | Что доказывает | Откуда |
|---|---|---|
| `max_user_id` с проверенной подписью | Это конкретный человек, а не аноним | initData |
| Телефон, подтверждённый MAX | Тот же человек, что и в аккаунте | `requestContact()` |
| QR квитанции | Он имеет отношение к этому лицевому счёту | Скан |

Ни одного из трёх по отдельности не хватает. Привязка лицевого счёта требует всех трёх.

### Два режима работы

Мини-приложения MAX «не могут существовать автономно», но наш сайт должен работать и вне MAX. Поэтому режим определяется наличием `window.WebApp`:

| | В MAX | В браузере |
|---|---|---|
| Вход | initData + подпись | QR квитанции |
| Второй фактор | `requestContact()` | нет (известное ограничение) |
| Скан QR | `openCodeReader()` | `getUserMedia` + jsQR |
| Назад | `BackButton` | `history.pushState` |
| Уведомления | Сообщения бота | Web Push |
| Приглашения | `shareContent` | код строкой |

Общий код один, различается только адаптер платформы. Это же защищает от привязки к одной платформе.

### Уведомления становятся настоящими

Вместо Web Push, который на iOS почти не работает, — сообщения бота с кнопкой `open_app`. Отправляем при смене статуса заявки, назначении мастера, аварийном отключении, напоминании о показаниях 20–25 числа и об оплате до 10-го.

Слой уведомлений всё равно пишем абстракцией над транспортом: в браузерном режиме остаётся Web Push.

## Что MAX по-прежнему не решает

**Юридическую значимость голосований.** ОСС по ЖК РФ требует подсчёта по долям в праве собственности, кворума, реестра собственников, протокола и размещения в ГИС ЖКХ. Подтверждённый аккаунт закрывает накрутку, но не законность. В MVP это остаётся **опросами**.

**Требование 152-ФЗ хранить ПДн в России.** Это про наш хостинг, а не про MAX.

**Отсутствие данных от УК.** Начисления по-прежнему приходят только из QR квитанции.

**Тему оформления.** См. выше — в Bridge её нет.

## Полноэкранного режима нет (проверено 28 августа 2026)

В Telegram с версии Bot API 8.0 у мини-приложений есть `requestFullscreen`.
**У MAX такого метода нет.** Проверено по самому мосту
`https://st.max.ru/js/max-web-app.js`: полный список событий, которые он
умеет отправлять, — `WebAppReady`, `WebAppClose`, `WebAppOpenLink`,
`WebAppOpenMaxLink`, `WebAppOpenCodeReader`, `WebAppShare`, `WebAppMaxShare`,
`WebAppRequestPhone`, `WebAppGetViewportSize`, `WebAppGetLaunchContext`,
`WebAppPlatform`, `WebAppVersion`, `WebAppDeviceName`, `WebAppDownloadFile`,
`WebAppChangeScreenBrightness`, `WebAppSetupBackButton`,
`WebAppSetupClosingBehavior`, `WebAppSetupSwipesBehavior`,
`WebAppHapticFeedbackImpact`, биометрия (`WebAppBiometry*`), хранилища
(`WebAppDeviceStorage*`, `WebAppSecureStorage*`) и NFC (`WebAppNfc*`).

Ни `fullscreen`, ни `expand`, ни `viewport`-подписки среди них нет: высоту
окна задаёт сам мессенджер, приложение может её только СПРОСИТЬ
(`WebAppGetViewportSize`).

Что даёт мост из близкого:

- `disableVerticalSwipes()` — забирает вертикальный свайп себе. Без этого
  тяга пальцем по длинному списку сворачивает мини-апп вместо прокрутки.
  Включено при старте (`platform.lockVerticalSwipes`).
- `requestScreenMaxBrightness()` — яркость на максимум, нужна при показе
  кода; для сканирования бесполезна.
- `WebAppDownloadFile` — скачивание файла средствами мессенджера.

Если полноэкранный режим появится, проверять надо здесь же: файл моста
отдаётся без версии в имени и обновляется на стороне платформы.


## Сканер мессенджера: почему свой идёт первым (28 августа 2026)

Владелец сообщил, что через MAX не сканируется даже случайный QR с экрана,
не говоря о квитанциях. Разобрали по самому мосту.

**Настроек у него нет вообще.** Весь контракт — одна строчка:

```js
openCodeReader(e = !0) {
  return this.requestController.createRequest("WebAppOpenCodeReader", { fileSelect: e }, { timeout: u });
}
```

Единственный параметр `fileSelect` решает, показывать ли кнопку галереи
в его окне. Ни чувствительности, ни зоны кадра, ни разрешения камеры,
ни списка форматов, ни приближения — ничего этого мессенджер наружу
не отдаёт. Когда его сканер не читает код, сделать с этим нельзя ничего.

**И он отдаёт строку, а не байты** — то есть выбирает кодировку за нас
и на `ST00011` (windows-1251) ошибается. Ремонт кодировки на сервере
(`lib/qr/encoding.ts`) закрывает часть случаев, но не те, где символы
уже заменены на U+FFFD.

**Итог: сканеров в приложении не осталось вовсе — только фотография.**

Сканер мессенджера убран потому, что чинить в нём нечего. Свой сканер
камерой убран по другой причине: `getUserMedia` требует ОТДЕЛЬНОГО
разрешения нашей странице — внутри мессенджера это второй запрос поверх
системного, и пожилой человек, увидев его внезапно, жмёт «Запретить».
Второй раз браузер уже не спросит, и путь закрывается навсегда.

Фотография не требует ни того, ни другого: снимок делает системная
камера, разрешение у неё уже есть, а к нам приходят БАЙТЫ в полном
разрешении — кодировку по заголовку кода мы читаем сами. Она же снимает
вопрос смазывания: человек снимает кадр, а не ловит фокус в потоке.

Что покажет бой: в логах каждой квитанции есть `source`. Соотношение
`camera` / `max` / `photo` внутри мессенджера и ответит, даёт ли MAX
камеру мини-приложениям на Android. До этого спорить не о чем.
